1. Co zostało zrobione

  • Na GitHubie (już działa): gałęzie dev i test utworzone z main, domyślna gałąź to dev, 8 otwartych PR-ów przekierowanych z main na dev, main przyjmuje zmiany tylko przez PR, etykieta back-to-dev.
  • CI (check.yml) uruchamia się dla dev, test i main oraz na żądanie.
  • Automat przepływu (flow.yml): zielony dev wchodzi na test; PR do test zawierający wyłącznie pliki testów scala się sam, a testy wracają na dev; zielony test otwiera PR test → main; czerwony test zakłada zgłoszenie back-to-dev; zmiana na main wraca na dev.
  • pr-decide (pr_gate.py): PR promocyjny scala commitem merge i nie usuwa gałęzi; zwykły PR nadal squash z usunięciem gałęzi.
  • Dokumentacja: ADR, sekcja w RUNBOOK, nowy CLAUDE.md repozytorium.

Poprawki 2026-11-15 (recenzja PR #84)

  • CI dla PR-ów w stosie: check.yml reaguje na każdy pull_request, nie tylko do dev/test/main.
  • Token: flow.yml używa sekretu FLOW_TOKEN, gdy istnieje (push uruchamia wtedy check sam i może zmieniać .github/workflows). Bez niego: GITHUB_TOKEN + ręczne uruchomienie check, a odrzucony push zmiany w workflows zakłada jedno zgłoszenie z poleceniem ręcznego pushu.
  • Zgłoszenia bez duplikatów: stałe tytuły; jeśli zgłoszenie o tym tytule jest otwarte, nowe nie powstaje (zgłoszenie o release jest odświeżane).
  • Wyścigi: wspólna grupa flow-write dla promote, tester-pr, sync; push ponawiany raz po scaleniu przesuniętej gałęzi; tester-pr bierze świeży dev przed scaleniem.
  • Release: PR test → main tylko, gdy test ma inną zawartość niż main (po synchronizacji same commity merge nie otwierają nowego PR-a); otwarty PR dostaje odświeżony opis.
  • pr-decide: merge-commit tylko dla gałęzi dev/test/main z repozytorium właściciela; PR z forka z gałęzią main idzie przez squash.
  • Logika kroków przeniesiona z YAML do ops/ci/flow_ops.py + flow_cli.py (testy jednostkowe).

3. Jak przetestować ręcznie (po scaleniu tego PR-a do dev)

  1. Zakładka Actions: po scaleniu przebieg check na dev, potem flow / promote. Gałąź test ma ten sam commit co dev.
  2. Przebieg check na test jest zielony, a flow / release-pr otwiera PR „release: test → main”. Jeśli zamiast PR-a pojawi się zgłoszenie z linkiem, włącz w ustawieniach repozytorium (Actions → General) zgodę na otwieranie PR-ów przez Actions.
  3. Otwórz PR do test, który dodaje tylko plik testu (np. ops/ci/tests/test_x.py). Po zielonym CI scala się sam, a dev dostaje ten plik.
  4. Otwórz PR do test, który zmienia plik z kodem. Nie scala się sam.
  5. Dodaj na test nieprzechodzący test (PR z samym testem). Po scaleniu pojawia się zgłoszenie back-to-dev, a PR promocyjny nie powstaje.
  6. Scal PR „release: test → main” przez „Dziś”. test nie znika, a flow / sync przenosi commit na dev.
  7. Pierwsze wydanie (raz): nie przez „Dziś”. Procedura w docs/RUNBOOK.md, „First release”: ochrona dev/test, ręczne gh pr merge <n> --merge bez --delete-branch, potem git pull w ~/code/logs-stack na uwh. Następne wydania już przez „Dziś”.

4. Ograniczenia i ryzyka

  • Do czasu scalenia tego PR-a PR-y celujące w dev nie mają CI, bo stary check.yml reaguje tylko na main. Ten PR powinien wejść pierwszy.
  • pr-decide na uwh działa z checkoutu main, więc nowy pr_gate.py trafi tam dopiero z pierwszym wydaniem. Pierwszy PR test → main scala się ręcznie (RUNBOOK, „First release”), inaczej squash usunąłby gałąź test.
  • Bez FLOW_TOKEN każda promocja zmieniająca .github/workflows wymaga ręcznego pushu (przypadek A).
  • GitHub trzyma jedno oczekujące zadanie na grupę flow-write: przy trzech naraz środkowe przepada. Zadania liczą stan gałęzi, więc następny zielony przebieg je powtarza; pominięty tester-pr wymaga ponownego uruchomienia jego check.
  • Konflikt przy automatycznym scalaniu gałęzi kończy się zgłoszeniem, nie próbą rozwiązania.
  • Nie ma osobnego środowiska testowego. Etap test uruchamia testy tras na Postgresie w CI.
  • Testera jeszcze nie ma jako stałej rutyny. Na razie to rodzaj zadania w kolejce sprintu.
