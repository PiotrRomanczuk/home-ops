Rejestr miejsc (storage_places) — lustro notatek vaulta w Postgresie

Data: 2026-11-12 · Gałąź: feat/storage-places · ADR: docs/adr/2026-11-12-storage-places.md · Plan w vaulcie: 3-Zasoby/analysis/2026-11-12-porzadek-wszystkich-miejsc.md

Co zostało zrobione

Rejestr miejsc z danymi (STORAGE.md) był jedną tabelą markdown. Od dziś każde miejsce to osobna notatka w 2-Obszary/mapy/miejsca/ z polami we frontmatterze (78 notatek). Ta zmiana dokłada lustro w Postgresie, tak jak dla notatek projektów:

  • Migracja 029 — tabela storage_places (klucz id = numer miejsca), statusy jako CHECK: porzadek ok / do-poprawy / problem / niesprawdzone, backup to samo + nie-wymaga / brak-oceny, stan aktywne / usuniete; daty sprawdzone i test_odtworzenia; sprawdzenie = polecenie do audytu.
  • agents/elitedesk/storage_md.py — parser notatek (tylko type: miejsce), wartości przechodzą bez zgadywania.
  • planner-sync — nowy krok storage_sync_once(): wysyła komplet na POST /api/storage/sync tylko gdy notatki się zmieniły (md5); odrzucone notatki loguje ze ścieżką.
  • POST /api/storage/sync (token) — walidacja w storage-model.ts, upsert po id, usunięcie id, których nie ma już w vaulcie, w jednej transakcji; pusty zestaw → 400, żeby zepsuty klon nie wyczyścił tabeli.
  • GET /api/storage (podgląd lub token) — miejsca wg id, filtry stan, porzadek, backup, gdzie, liczniki statusów.
  • CI: migracja 029 w zestawie integracyjnym + storage.test.ts.

Jak przetestować ręcznie

  1. Parser na prawdziwym vaulcie (Mac, bez hosta):
    cd home-ops && python3 -c "
import importlib.util,pathlib,collections
s=importlib.util.spec_from_file_location('m','agents/elitedesk/storage_md.py');m=importlib.util.module_from_spec(s);s.loader.exec_module(m)
p=m.parse_places(pathlib.Path.home()/'Obsidian/MainCV-Planner')
print(len(p), collections.Counter(x['backup'] for x in p))"
    Oczekiwane: 78 i liczniki backupu (26 × problem).
  2. Deploy na uwh (po merge, z czystego main): 
    git pull
scripts/apply-migrations.sh                     # 029_storage_places
docker compose up -d --build ingest
scripts/deploy-agent.sh elitedesk planner-sync   # planner-sync.py + storage_md.py
  3. Sync: w logach planner-sync (źródło agent:planner-sync) w ciągu 60 s linia storage sync ok z upserted: 78. Potem 
    curl -s -H "X-Ingest-Token: …" "http://192.168.1.75:64421/api/storage?backup=problem" | jq '.summary'
    Oczekiwane: total 26.
  4. Zmiana w Obsidianie: w notatce 74-onedrive.md zmienić backup: niesprawdzone → backup: ok. Po ≤ 60 s (pull lustra + tick) GET pokazuje nową wartość; bez zmian w notatkach kolejne ticki nie wysyłają nic (brak nowych linii storage sync ok).
  5. Brzegi: wpisać porzadek: 🟢 w jednej notatce → linia storage sync ok na poziomie warn z rejected: [{note: …, reason: "bad status value"}], reszta miejsc się zapisuje; usunąć notatkę → jej id znika z tabeli (removed: 1); POST bez tokena → 401; {"places": []} → 400.
