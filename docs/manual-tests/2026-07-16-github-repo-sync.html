1. What was actually done

home-ops already tracked basic project state (status, Now/Next/Later) synced from the Obsidian vault, but last_commit/commits_30d were hand-typed frontmatter, not real git data, and there was no stack/version/deploy-reachability tracking at all. This adds a second, independently-refreshed data layer for Piotr's other MainCV projects (strummy, landing-portfolio, inborr, shortscannon, etc.) — computed server-side on elitedesk, with no new process on his Mac.

ChangeBehavior nowFiles
New repo_meta/repo_synced_at columns Additive to the existing projects table — never overwrites the vault-owned columns (title, status, now_md/etc., raw_frontmatter). postgres/migrations/016_project_repo_meta.sql
New POST /api/projects/repo-sync UPDATE-only — unlike /api/projects/sync, it never inserts or deletes a row. A slug with no matching project is reported back in unknownSlugs, not silently created. Row existence stays owned by the vault sync path. ingest/src/routes/projects.ts
github-repo-sync.py (new, runs on elitedesk only) Every 4h: per mapped project, pulls stack/version/commit-activity from the GitHub API (or a direct local git log for stano, whose remote is a bare repo already on elitedesk, not GitHub), plus a deploy-URL reachability check — run from elitedesk specifically so it never flaps with Piotr's laptop sleeping. POSTs the batch to /api/projects/repo-sync. ops/elitedesk/github-repo-sync.py, github-repo-sync.projects.json, github-repo-sync.{service,timer,env.example}

3. Test 1 — repo-sync is UPDATE-only

The core contract this whole design leans on: repo-sync must never create or delete a projects row.

Verified via ingest/src/routes/__tests__/projects-repo-sync.test.ts against a real Postgres (not mocked) — 6/6 passing:
cd ingest
DATABASE_URL=postgresql://postgres@127.0.0.1:5432/home_ops \
INGEST_TOKEN=ci-token LOGS_PASSWORD=ci-password \
npm test -- --run src/routes/__tests__/projects-repo-sync.test.ts

# ✓ updates repo_meta + repo_synced_at for an existing slug
# ✓ reports unknown slugs and never creates a row for them
# ✓ never touches vault-owned columns (title/status/now_md)
# ✓ requires a token
# ✓ rejects a non-array entries payload
# ✓ GET /api/projects and GET /api/projects/:slug include repo_meta + repo_synced_at

To re-check by hand: POST /api/projects/repo-sync with a slug that doesn't exist in projects, then SELECT count(*) FROM projects WHERE slug='that-slug' — must be 0.

5. Test 3 — Projects tab renders the new fields

With the ingest server + seeded rows from Test 2 still running, open http://127.0.0.1:58080/#tab=projects (or the real console once deployed).

Expected:
  • strummy's grid card shows a small v0.160.0 badge next to the health emoji/deploy chip, and the deploy chip has a green dot (reachable).
  • Click into strummy's drill page — the title row shows the version badge; the deploy link has a green dot and its title tooltip (hover) reads "reachable · checked N ago"; a new "repo data" line under the stack line reads computed 77 commits/30d, last 2026-07-14 · synced N ago.
  • rhcsa-lab's drill page shows a "repo data" line with the unsupported reason instead of a commits count.
  • The section bar (top of the Projects tab) shows both · vault sync N ago and · repo data N ago — two independent freshness labels, since the two producers run on different schedules (60s vs 4h).
  • A project with no repo_meta at all (never synced) shows none of the above — no stray empty badges or dots.

6. Edge cases worth checking

  • GITHUB_TOKEN missing: the script still runs and POSTs, but every owner_repo entry likely degrades to {"error": "GET ... failed"} once GitHub's 60/hr anonymous limit is hit (this session had headroom left, so strummy above got real data on an unauthenticated run — don't rely on that lasting; set GITHUB_TOKEN before enabling the timer for real).
  • A vault slug renamed/removed: the mapping file (github-repo-sync.projects.json) is hand-maintained and won't auto-follow a vault rename — a stale entry just shows up in unknownSlugs each run (harmless, but worth pruning).
  • justmeandguitars' two nested repos: only overlay-app is tracked per the mapping file's _note — confirm that's still the right call once the planning/ repo has meaningful activity too.
  • Deploy URL that's actually down: point deploy_url at something that 404s or times out and confirm the drill page's dot goes red / the chip's tooltip shows "unreachable" rather than crashing the render.
