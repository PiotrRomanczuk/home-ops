1. What was actually done

Everything in home-ops observes the world through elitedesk — Postgres, ingest, digest, github-repo-sync all live there. The dead-agent sentinel (migration 010) alerts by inserting into host_logs, a table that dies with the host, so elitedesk going down was the one failure the stack could not report about itself. And with only one reachability prober (elitedesk), its own egress hiccup made every project look "down" at once. rpi-sentinel closes both gaps from the Pi — always-on, separate failure domain, ~5W (the one host where recurring background work is guilt-free after the electric-bill decision).

ChangeBehavior nowFiles
Watchdog loop Polls GET /api/health (covers ingest + Postgres in one call) every 60s. 3 consecutive failures → alert email sent directly from the Pi via stdlib smtplib (Gmail app password from a 0600 file, the send-digest.py pattern) — the alert path does not touch elitedesk. Re-alerts every 4h while down. On recovery: recovery email + a retroactive outage record posted into host_logs (it couldn't log during the outage — the log store was the thing that was down). agents/rpi/rpi-sentinel.py

Transition-only: up→down (2 consecutive failed rounds + a same-tick retry) posts an error event with source='app:<slug>', down→up posts an info recovery event. 3. How to deploy to the Pi

  1. Put the Gmail app password on the Pi (same credential the digest uses on elitedesk): 
    ssh rpi "mkdir -p ~/.config/home-ops && umask 177 && cat > ~/.config/home-ops/smtp.pass"
# paste the app password, Ctrl-D
  2. Create ~/.config/rpi-sentinel.env on the Pi: 
    INGEST_URL=http://192.168.1.75:64421/api/ingest
INGEST_TOKEN=<shared token, same as rpi-watcher.env>
ALERT_TO=p.romanczuk@gmail.com
ALERT_FROM=p.romanczuk@gmail.com
  3. Deploy + enable (the script's rpi branch already existed — no changes needed): 
    scripts/deploy-agent.sh rpi rpi-sentinel
ssh rpi "systemctl --user enable rpi-sentinel"

4. Live verification on the Pi

  • ssh rpi "journalctl --user -u rpi-sentinel --since '2 min ago'" — shows no errors; the console's Logs tab shows the agent:rpi-sentinel "up" event.
  • After ~10 min, no app:* events from host rpi should exist (all deploys up — silence is the success state).
  • Fire drill (recommended once): ssh uwh "docker stop home-ops-ingest-1" → an alert email should arrive within ~4 min → docker start home-ops-ingest-1 → recovery email + an ingest outage over error row in the Logs view.
  • Probe drill: temporarily add a bogus deploy_url to one project in elitedesk's github-repo-sync.projects.json, wait for its next 4h tick (or run it once by hand), then within ~20 min the sentinel posts an app:<slug> error visible on that project's drill page. Revert after.

5. Edge cases worth checking

  • Alert channel broken (bad app password, Gmail down): send_alert returns False and logs to stderr/journald — the sentinel keeps running (unit-tested; worth eyeballing journald after the first real alert).
  • Pi reboot: unit is WantedBy=default.target with Restart=on-failure, same as rpi-watcher — confirm it comes back after ssh rpi sudo reboot.
  • Both probers down-vote: when a deploy is genuinely down, expect BOTH the red dot (elitedesk's repo_meta, ≤4h stale) AND an rpi event (≤20 min fresh) — the rpi event will usually arrive first.
  • No repo_meta yet: if github-repo-sync hasn't run, the sentinel falls back to raw_frontmatter.deployed URLs from the vault — probing still works.
