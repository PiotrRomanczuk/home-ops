1. Co zostało zrobione

Przegląd wszystkich 13 magazynów danych w ~/code pokazał, że zbiory danych zbierane przez zadania (song2logic, job-radar, d4, daily-news, olx-scraper) robią to samo każdy inaczej. Z tego powstał szablon do skopiowania (nie biblioteka) w templates/dataset-db/:

  • Miejsce: własny schemat w home_ops, więc nocny pg-backup obejmuje go od pierwszego dnia.
  • Zapis z Maca: ssh uwh docker exec -i home-ops-postgres-1 psql (wzorzec song2logic): bez sterownika, hasła i otwartego portu (db/psql.py).
  • Migracje z rejestrem (db/migrate.py): pliki NNN_nazwa.sql, tabela <schemat>.schema_migrations z sumą SHA-256, każdy plik w jednej transakcji, a plik zmieniony po zastosowaniu zatrzymuje przebieg. Tego brakowało job-radar.
  • Ładowanie (db/load.py): JSONL → COPY do tabel tymczasowych → upsert projektu → strażnik liczby wierszy (tabela, w której ubyło wierszy, przerywa cały zapis: lekcja z olx-scraper 12.10 i Strummy dev 10.11) → commit albo rollback przy --dry-run.
  • Szkielet migrations/001_init.sql: tabela runs, przykładowa tabela items (klucz naturalny, raw jsonb, first_seen_at/last_seen_at, check zamiast enumów), widok i rola tylko do odczytu <schemat>_ro.
  • Konwencje z pochodzeniem każdej reguły w templates/dataset-db/README.md; decyzja w docs/adr/2026-11-14-dataset-db-template.md; nowy rozdział w docs/CONTEXT.md.
  • scripts/new-dataset.sh <schemat> <pakiet> kopiuje szablon i wstawia nazwę schematu oraz datę.
  • CI: nowy job tests-dataset-db (Postgres 17 jako usługa, testy czyste i na żywej bazie, próba new-dataset.sh).

Nic nie zostało zastosowane na uwh. Pierwszym użytkownikiem będzie coupon-ocr (schemat zakupy) w osobnym repo.

3. Jak przetestować ręcznie

Wymagania: Docker (na Macu Colima), Python ≥ 3.12.

docker run -d --rm --name dataset-db-test -e POSTGRES_PASSWORD=x postgres:17-alpine
cd ~/code/homelab/home-ops/templates/dataset-db
DATASET_TEST_PSQL="docker exec -i dataset-db-test psql -U postgres -d postgres" \
  python3 -m unittest discover -s tests -t . -v
# oczekiwane: Ran 17 tests … OK

Ręczna próba całego cyklu na tej samej bazie:

T=$(mktemp -d)
~/code/homelab/home-ops/scripts/new-dataset.sh demo $T/pkg
cd $T/pkg
export DATASET_PSQL="docker exec -i dataset-db-test psql -U postgres -d postgres"
python3 -m db.migrate --schema demo --dir migrations --dry-run   # would apply 1: 001_init.sql
python3 -m db.migrate --schema demo --dir migrations             # applied 1
python3 -m db.migrate --schema demo --dir migrations             # applied 0
echo '-- edit' >> migrations/001_init.sql
python3 -m db.migrate --schema demo --dir migrations             # ✗ changed after being applied: 001_init.sql
docker stop dataset-db-test

Przypadki brzegowe warte sprawdzenia: plik 1_a.sql albo dwa pliki 001_* w migrations/ (odmowa przed dotknięciem bazy); new-dataset.sh drugi raz w ten sam katalog (odmowa, nic nie nadpisane).

4. Czego to nie robi

  • Nie zmienia song2logic ani job-radar (przeniesienie na szablon to osobny plan).
  • Zapis idzie jako postgres (ograniczenie opisane w ADR); czytelnicy dostają rolę _ro.
  • scripts/apply-migrations.sh nie dotyka schematów zbiorów danych.
