pr-review — „druga para oczu” dla wszystkich PR

Data: 2026-11-11 · Gałąź: feat/pr-review · Zakres: R1 (recenzent), R2 (pr-decide), R5 (migracja 028)

1. Co zostało zrobione

Zasada z pracy Piotra: autor zmiany nie może jej zaakceptować. Do tej pory pr-decide pytał na „Dziś” o każdy otwarty PR i po „Scal” scalał go bez żadnej recenzji. Teraz:

  • pr_review.py (timer co godzinę 07–23): każdy otwarty PR, którego bieżący commit nie ma recenzji, dostaje niezależną recenzję — świeży claude -p (Opus, subskrypcja), tylko narzędzia odczytu w checkoutcie PR, bez wiedzy o sesji, która pisała kod. Dwa przebiegi: znajdź uwagi → zweryfikuj każdą w kodzie (niepotwierdzone odpadają). Wynik: komentarz w PR (z markerem SHA), etykieta review:ok/review:zmiany, wiersz w pr_reviews, karta na „Dziś”. Maks. 3 PR na przebieg.
  • pr_decide.py + pr_gate.py: pyta o PR dopiero po recenzji jego bieżącego commitu. Opcje wg recenzji: ok → Scal / Odrzuć / Później; uwagi → Popraw / Scal mimo to / Odrzuć / Później; po 2 rundach poprawek bez „Popraw”. „Popraw” = etykieta fix-requested dla pr-agent (osobny PR w repo infrastructure). Pytanie niesie SHA zrecenzowanego commitu, a scalenie idzie z --match-head-commit — odpowiedź nigdy nie scali nowszego, nieprzejrzanego kodu. Pytanie o starszy commit jest automatycznie zastępowane (nie dubluje się na „Dziś”).
  • Migracja 028 pr_reviews (lokalny Postgres home-ops), numer 028, bo 025 i 027 są zajęte na innych gałęziach.
  • Diff dla recenzenta pomija raporty HTML ze zrzutami i pliki blokad (vectordigital#7: 4 MB z 4,3 MB to base64) i mówi, co pominął.
  • Reguła dla sesji Claude (vault, branch-hygiene.md): sesja-autor nigdy nie scala ani nie zatwierdza PR.

3. Jak przetestować ręcznie (po scaleniu)

ssh uwh
cd ~/code/logs-stack && git pull
docker exec -i home-ops-postgres-1 psql -U postgres -d home_ops -v ON_ERROR_STOP=1 < postgres/migrations/028_pr_reviews.sql
python3 ops/elitedesk/pr_review.py --dry-run --pr vectordigital#7     # plik w ~/.cache/pr-review/dry/, nic na GitHubie, nic w bazie
cp ops/elitedesk/pr-review.{service,timer} ~/.config/systemd/user/ && systemctl --user daemon-reload
systemctl --user enable --now pr-review.timer
systemctl --user start pr-review.service && journalctl --user -u pr-review -n 30
  1. Na GitHubie: 3 najstarsze otwarte PR mają komentarz „Recenzja automatyczna — …” i etykietę review:ok albo review:zmiany.
  2. SELECT repo, number, left(head_sha,7), verdict, dropped, cost_usd FROM pr_reviews ORDER BY created_at DESC; — 3 wiersze.
  3. Na „Dziś”: karta pr-review; po najbliższym pr-decide (08:05/19:05) pytania tylko o zrecenzowane PR, z opcjami wg werdyktu i streszczeniem recenzji w szczegółach.
  4. Nowy commit na zrecenzowanym PR → kolejny przebieg recenzuje nowy SHA; stare pytanie znika (odpowiedź „Później”, powód „zastąpione nowym commitem”), pojawia się nowe.
  5. „Scal” po dopchnięciu commitu bez recenzji → w logu head moved … not merging unreviewed code, PR zostaje otwarty.

4. Ograniczenia i ryzyka

  • Zaległość: 27 otwartych PR → ok. 9 przebiegów (1 dzień); stare PR warto najpierw zamknąć, żeby nie zużywać subskrypcji.
  • Recenzja jest niedeterministyczna (dwa przebiegi na tym samym PR dały różne drobne uwagi); dlatego decyzję podejmuje Piotr, a weryfikator odsiewa fałszywe alarmy.
  • Treść PR może zawierać próbę wstrzyknięcia poleceń — recenzent ma tylko odczyt w checkoutcie, publikuje skrypt (nie sesja).
  • „Popraw” działa dopiero po wdrożeniu pr-agent (osobny PR w infrastructure + konfiguracja użytkownika przez Piotra).
