Po co

uwh odpala 32 timery systemctl --user i dwa runnery GitHub Actions, ale żadne z tych uruchomień nie trafiało do home-ops. Hałas o 19:20 (Strummy „Nightly E2E”: Playwright z nagrywaniem wideo, load 17 na 8 rdzeniach) nie był nigdzie widoczny. Ten PR zbiera dane, a zakładka je pokaże.

Co zostało zrobione

  • Nowy agent activity-watcher (systemd --user na elitedesk, ten sam plik env co elitedesk-watcher):
    • co 30 s czyta journal --user od zapisanego kursora; przy pierwszym starcie robi backfill 7 dni;
    • z komunikatów systemd (start, koniec, porażka, „Consumed … CPU”) składa jedno uruchomienie na INVOCATION_ID, z kodem wyjścia, CPU, pamięcią i ostatnimi 30 liniami logu;
    • śledzi tylko unity z ~/.config/systemd/user, bez szumu sesji pulpitu;
    • projekt przypisuje według wzorców nazw (seo-* → gitara-lekcje itd.), a w razie braku według WorkingDirectory=~/code/<repo>;
    • pętla restartów to jeden wiersz: kolejne porażki tego samego unitu w ciągu 10 min podbijają repeat_count;
    • logi krótkich procesów: journald gubi unit procesu, który kończy się w < 1 s. Taka linia trafia do jedynego oneshota trwającego w tej chwili, a gdy trwają dwa, jest pomijana, bo żaden log jest lepszy niż cudzy.
  • Joby GitHub Actions: co 2 min przez gh api (gh na uwh jest już zalogowany, nowy token nie jest potrzebny). Repo wykrywane są z ~/actions-runner/*/.runner. Zostają tylko joby z runnerów uwh-*; każdy ma link do GitHuba.
  • Migawka „teraz”, co 30 s:
    • CPU zgrupowane per właściciel z /proc/<pid>/cgroup (runner, kontener, unit), czyli Playwright = „github-runner-strummy”, a nie 40 procesów chrome;
    • trwające oneshoty, zajętość runnerów, 5 najbliższych timerów.
  • Migracja 026:
    • unit_runs: upsert po (host, invocation_id); późniejszy POST nie kasuje tego, co wiedział wcześniejszy;
    • activity_now: 1 wiersz na hosta;
    • pg_cron czyści runy starsze niż 90 dni.
  • API:
    • POST /api/activity/runs i /now (token);
    • GET /api/activity/now: migawki + podsumowanie 24 h (runy, porażki, które unity padają);
    • GET /api/activity/runs?since_h&project&unit&result&kind;
    • GET /api/activity/runs/:id: z logiem.
  • Poprawka: elitedesk-watcher.py nie miał import json (od d3a272b), więc wątki journald padały na pierwszej linii. Nowy test test_agent_imports.py sprawdza to dla wszystkich agentów.

Jak przetestować ręcznie (po merge'u)

  1. Na uwh: 
    cd ~/code/logs-stack && git pull
scripts/apply-migrations.sh
docker compose up -d --build ingest
# z Maca:
scripts/deploy-agent.sh elitedesk activity-watcher
scripts/deploy-agent.sh elitedesk elitedesk-watcher   # poprawka import json
  2. systemctl --user status activity-watcher pokazuje active; w logu jest „activity-watcher up: … cursor=backfill -7d”.
  3. curl -s http://192.168.1.75:64421/api/activity/now -H "X-Ingest-Token: …" | jq .summary_24h: runy > 0, a w failing_units stano-backfill i szczerze-mowiac-replies.
  4. Po najbliższym kwadransie /api/activity/runs?unit=lesson-notes-social.service ma nowy run z result: ok.
  5. Gdy biegnie Nightly E2E (~08:17, 15:19, 19:20), snapshot.runners[].busy = true, a w owners na górze jest github-runner-strummy.
  6. Restart agenta (systemctl --user restart activity-watcher) nie robi duplikatów, bo czyta od kursora ~/.local/state/home-ops/activity.cursor.

Przypadki brzegowe: dwa timery startujące w tej samej sekundzie (np. :30 lesson-notes-social + social-hub-cron) mają logi bez metadanych; trafiają one tylko tam, gdzie da się je jednoznacznie przypisać. Prywatność: logi zostają w bazie home-ops w LAN; repo zawiera tylko kod.
