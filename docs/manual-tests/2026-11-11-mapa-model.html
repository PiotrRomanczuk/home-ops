Jak przetestować ręcznie

1. Testy

python3 -m unittest discover -s agents/tests -p 'test_*.py'          # 108 OK (w tym vault_parse, vault_processes)
cd ingest && npm run check && npm test -- --run                   # unit: map-model, process-model

2. Integracja na jednorazowym Postgresie

docker run -d --rm --name mapa-test-pg -e POSTGRES_PASSWORD=ci-placeholder -e POSTGRES_DB=home_ops \
  -p 127.0.0.1:55499:5432 postgres:17-alpine
for f in 001_init 004_cancelling_status 005_projects 016_project_repo_meta 029_processes 029_processes; do
  docker exec -i mapa-test-pg psql -q -U postgres -d home_ops -v ON_ERROR_STOP=1 < postgres/migrations/$f.sql; done
cd ingest && DATABASE_URL=postgresql://postgres:ci-placeholder@127.0.0.1:55499/home_ops INGEST_TOKEN=ci-token \
  LOGS_PASSWORD=ci-password npx vitest --run src/routes/__tests__/processes-map.test.ts     # 5 passed
docker stop mapa-test-pg

Oczekiwane: sync bez tokena daje 401; drugi sync usuwa nieobecny slug (removed: 1); lista nie ma bpmn_xml, a szczegół go ma; zły payload daje 400 i tabeli nie rusza; mapa łączy projekty, zewnętrzne, hosty i procesy.

3. Po wdrożeniu na uwh

Kolejność: najpierw ingest i migracja, potem planner-sync. W odwrotnej kolejności planner-sync zaloguje jeden raz „process sync failed: status=404” i zamilknie do zmiany wyniku.

ssh uwh 'cd ~/code/logs-stack && git pull && scripts/apply-migrations.sh && docker compose up -d --build ingest'
scripts/deploy-agent.sh elitedesk planner-sync          # kopiuje też vault_parse.py / vault_processes.py do ~/bin
curl -s -H "X-Ingest-Token: $INGEST_TOKEN" http://192.168.1.75:64421/api/map | jq '.processes | length'   # 5
curl -s -H "X-Ingest-Token: $INGEST_TOKEN" http://192.168.1.75:64421/api/map \
  | jq -r '.nodes[] | select(.dependents|length>0) | "\(.id) → \(.dependents|join(", "))"'

W zakładce Logs, źródło agent:planner-sync, ma się pojawić jedno „process sync ok”, a stary „sync ok” dla projektów dalej co minutę. Strummy prod nie jest dotykany (przebudowa dotyczy tylko kontenera ingest). Kontrola z reguły i tak obowiązuje: 10 kontenerów supabase_*_StudentProduction Up, curl -sI https://strummy.online → 200.

4. Pętla „vault jest źródłem prawdy”

  1. W Obsidianie dopisz w dowolnej notatce projektu depends_on: ["[[home-ops]]"] (albo przez panel Properties jako listę).
  2. Po pushu obsidian-git (do 5 min) i jednym ticku planner-sync (60 s) /api/map pokazuje nową krawędź, a home-ops.dependents zawiera ten projekt.
  3. Zmień nazwę lane w procesy/*.bpmn na nieznaną → /api/processes zwraca ostrzeżenie „lanes missing from projects: …”.

Przypadki brzegowe pokryte testami

  • Skalary z przecinkiem (stack: Python, uv) i cytowany "[a, b]" zostają stringami. Goły [[x]] to skalar, nie lista.
  • Pozycja listy z dwukropkiem (URL) nie staje się kluczem. Komentarz # … na końcu pozycji jest ucinany.
  • Cykle w depends_on nie zawieszają liczenia blast radius.
  • Duplikat sluga procesu: pierwszy wygrywa, drugi trafia do ostrzeżeń planner-sync.
  • bpmn: ../../../x.bpmn nie wychodzi poza folder notatki.
