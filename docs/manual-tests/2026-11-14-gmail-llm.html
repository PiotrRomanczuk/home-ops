Gmail: Claude proponuje reguły, człowiek zatwierdza

2026-11-14 · gałąź feat/gmail-llm (na feat/gmail-cleanup, PR #68) · ADR docs/adr/2026-11-13-gmail-llm-rule-proposals.md · test na bazie gmail_test (uwh), bez dostępu do Gmaila (token martwy od 31.10)

Co zostało zrobione

  • Claude pisze propozycje reguł, nie etykiety. Dla nadawców, których żadna reguła nie łapie (koszyki none / tab / unsub), Claude proponuje: nadawca (adres albo domena) → kategoria z istniejącej listy + polityka skrzynki keep/archive. Zatwierdzona propozycja staje się zwykłym wierszem gmail.rule, więc reconcile_live jej nie cofa.
  • Wywołanie: claude -p na abonamencie Max, paczki po 20 nadawców, --json-schema (kategoria i nadawca jako enum), przy każdej kategorii kilku przykładowych nadawców z reguł. CLI odchudzone flagami --tools '', --strict-mcp-config, --setting-sources '', własny --system-prompt: ok. 1 tys. tokenów narzutu zamiast ok. 570 tys.
  • Migracja 031: gmail.rule.inbox, tabela gmail.rule_proposal, rules_json() zwraca inbox.
  • Rutyna gmail-daily: consume odpowiedzi z „Dziś” → klasyfikacja → propose (≤ 40 nadawców) → ask (≤ 3 otwarte pytania) → archive według zatwierdzonych reguł. Nigdy Kosz; chronione maile (gwiazdka, chronione kategorie, tematy jak dokumenty) nigdy nie są archiwizowane. GMAIL_LLM=0 wyłącza całość.
  • Przegląd w terminalu: gmail_review.py (t / z / a / n / p / q). CLI ręczne: gmail-llm.py propose|archive|ask|consume działa bez Gmaila.
  • Ewaluacja: gmail_llm_eval.py + gmail_llm_report.py — zgodność z istniejącymi regułami (reguł model nie widzi; przykłady nigdy z domeny ocenianej w tej samej paczce).
  • Przy okazji: test test_automated_only_subject_rule_skips_people nie był uruchamiany przez unittest (funkcja w stylu pytest za if __name__) — przeniesiony do klasy.

Jak przetestować ręcznie (po scaleniu PR #68 i tego PR)

  1. Wymagania Piotra: GCP home-ops-seo → ekran zgody → In production; nowy token na Macu (gmail_cleanup.py auth); scp ~/.config/home-ops/gmail-{client,token}.json uwh:~/.config/home-ops/; w gmail-daily.env wpisać CLAUDE_CODE_OAUTH_TOKEN (ten sam co w seo-collect.env).
  2. Na uwh: cd ~/code/logs-stack && git pull && scripts/apply-migrations.sh (025 + 031), python3 ops/elitedesk/gmail_import.py all.
  3. python3 ops/elitedesk/gmail-llm.py propose --limit 10 --dry — oczekiwane: 10 linii proposal: nadawca → kategoria / keep|archive (pewność), nic nie zapisane.
  4. python3 ops/elitedesk/gmail-llm.py propose, potem ssh -t uwh 'cd ~/code/logs-stack && python3 ops/elitedesk/gmail_review.py' — przejrzyj kilka; z pokazuje listę kategorii, a przełącza skrzynkę/archiwum, n = nadawca nie wróci.
  5. python3 ops/elitedesk/gmail-llm.py archive — ile maili zarchiwizuje najbliższy przebieg; sprawdź, że maile z gwiazdką nie są liczone.
  6. systemctl --user start gmail-daily.service && journalctl --user -u gmail-daily -n 30 — karta na „Dziś” z „propozycji reguł N, zarchiwizowanych M” i do 3 pytań Gmail: … → kategoria? (tak / tak, ale w skrzynce / nie).
  7. Cofnięcie archiwizacji: python3 ops/elitedesk/gmail_cleanup.py undo ~/.local/state/home-ops/gmail/journal-daily-<czas>.jsonl przywraca INBOX.
